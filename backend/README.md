# Customer 360 backend

The backend uses Atlas Managed MCP for all runtime database operations, including
file content. It reads MCP credentials, `MDB_MCP_PROJECT_ID`,
`MDB_MCP_CLUSTER_NAME`, and `MONGODB_DATABASE` from the process environment or
`database/.env`. `MONGODB_URI` is not needed or read by the API.

The existing hackathon database is already provisioned. Start from the repository root:

```powershell
python -m venv backend\.venv
backend\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
Set-Location backend
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000
```

Each new onboarding chat creates a distinct customer and anonymous applicant
record. The applicant satisfies the existing required `created_by` reference;
its generated `.invalid` email is a placeholder, not a contact address or login.
Retries use stable IDs derived from the chat UUID. Resuming a chat uses its
stored customer ID. Login remains a demo entry point; the selected demo persona scopes conversation history and submitted applications.
The persona picker is unauthenticated and intended for sandbox data.
Existing chats keep their original links. Saved answers
update `customers.legal_name`, `business_activity`, `registration_location`, and
`ownership_description`; the onboarding application stores these named fields
plus `banking_needs` and the original answers. Compound free-text responses are
not guessed into structured `owners`, `industry`, `address` or product codes.
These additional string fields are permitted by the existing collection validators.

The demo also stores
onboardings, conversations, messages, document metadata and document content in
Atlas. File content uses GridFS; the `fs.files` and `fs.chunks` collections are
created automatically on the first upload if absent. MCP writes BSON binary
chunks and reads them back through CRUD tools. Existing GridFS files remain
readable. The Atlas MCP configuration must permit database reads and writes.
Existing local browser conversations are migrated on first load. The login
endpoint still returns `true` without credentials and is not authentication.
Uploads accept PDF, DOCX, TXT, CSV, PNG or JPG files up to 10 MB, with up to 10
files per conversation. Documents can be downloaded or deleted; they are not
scanned or processed by an agent.

`CORS_ORIGINS` accepts comma-separated browser origins, falling back to
`FRONTEND_ORIGIN` and then `http://localhost:5173`. Run the endpoint
tests from `backend/`:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests
```

## Atlas Managed MCP

`app/mongodb_mcp.py` connects directly to MongoDB's hosted MCP server at
`https://mcp.mongodb.com` using Streamable HTTP. It obtains OAuth tokens from
Atlas using client credentials, caches them in memory and refreshes them before
expiry. No Node.js package, local MCP server or npx proxy is required.

Add the following variables to the existing `database/.env`, or set them in the
process environment. See `database/.env.example` for a credential-free template.
Keep `MONGODB_DATABASE` set to the existing database name.

```dotenv
MDB_MCP_API_CLIENT_ID=<your MCP configuration client ID>
MDB_MCP_API_CLIENT_SECRET=<newly rotated client secret>
MDB_MCP_API_BASE_URL=https://mcp.mongodb.com
MDB_MCP_PROJECT_ID=<sandbox project ID>
MDB_MCP_CLUSTER_NAME=<cluster name>
MONGODB_DATABASE=<existing database name>
CORS_ORIGINS=http://localhost:5173
```

Use credentials generated by the **Atlas Managed MCP** configuration. Rotate any
secret previously shared in chat. Keep the replacement only in local environment
variables or the ignored `database/.env`. The API needs CRUD permissions: a
read-only MCP configuration cannot support creating conversations or uploads.
Set appropriate project roles in Atlas; the client does not change those roles.
Allow the backend's IP in that configuration's API access list when required.

From the repository root:

```powershell
backend\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
Set-Location backend
.\.venv\Scripts\python.exe -m app.mongodb_mcp
```

This verifies OAuth, the MCP handshake and tool discovery. For a database check,
also set `MDB_MCP_PROJECT_ID`, `MDB_MCP_CLUSTER_NAME`, and `MONGODB_DATABASE`, then:

```powershell
.\.venv\Scripts\python.exe -m app.mongodb_mcp --check-database
```

The check calls `remote-atlas-connect` and passes its returned `connectionId`
to `list-collections`. It prints confirmation without customer records. Cluster
connection may require additional Atlas permissions; it does not use the old
local server's `preconfigured` connection.

An internal agent can use the client directly:

```python
from app.mongodb_mcp import mongodb_mcp_session

async with mongodb_mcp_session() as session:
    tools = await session.list_tools()  # Tool names and argument schemas
    # Call discovered tools using session.call_tool(name, arguments).
```

Enter and exit the context in the same async task and keep it open for the agent
run. The LangGraph/LLM workflow is still pending. All REST API persistence goes
through `app/mcp_database.py` using `find`, `update-many`, `insert-many` and
`delete-many`. BSON codecs from the PyMongo package preserve ObjectIds, dates
and binary data; the runtime creates no MongoClient or GridFS driver connections.

Files use 16 KiB chunks to fit hosted MCP request limits; reads also support the old
GridFS chunk size. Upload limits remain 10 MB and 10 files per conversation.
Requests are serialized inside the single demo process to protect multi-step
writes. Run one Uvicorn worker. MCP operations are separate remote calls, not a
transaction; partial writes and interrupted uploads can require cleanup. This
path has more latency than a direct driver.

For an opt-in live test (creates and removes its own synthetic test records):

```powershell
$env:RUN_ATLAS_INTEGRATION='1'
.\.venv\Scripts\python.exe -m unittest discover -s tests -p test_atlas_live.py -v
```

`database/init_database.py` is a separate, legacy provisioning utility. It still
uses a direct URI to create validators and unique indexes that the hosted MCP
tools cannot configure. It is not part of API startup and is unnecessary for the
already-provisioned sandbox. For a new database, provision the definitions in
`database/collections.json` through Atlas or that utility before running the app.

The Codex TOML configuration is separate: it connects Codex to the managed MCP
server through the npx proxy. This backend instead calls the hosted server
directly, following MongoDB's recommendation for programmatic agents.

References: [MongoDB setup](https://www.mongodb.com/docs/mcp-server/get-started/),
[managed MCP overview](https://www.mongodb.com/docs/mcp-server/overview/).

## Onboarding chatbot MVP

Open the customer demo and select business onboarding. FastAPI supplies the
questions, tracks progress, and saves chat turns and accepted answers in Atlas.
The existing conversation history can resume previously saved drafts.

The chatbot starts in guided mode with MongoDB alone. To enable model-assisted
follow-ups, install the updated backend requirements and the LangChain
integration package for your chosen provider. Set `ONBOARDING_CHAT_MODEL` to
`provider:model` and configure that provider's credentials before starting
Uvicorn. Choose a chat model that supports LangChain structured output.

FastAPI loads the Git-ignored `backend/.env` for model settings and then loads
`database/.env` for Atlas settings. Process environment variables take
precedence. For the Gemini Developer API, install `langchain-google-genai` and
set these values in `backend/.env`:

```dotenv
GOOGLE_API_KEY=your_gemini_api_key
GOOGLE_GENAI_USE_VERTEXAI=false
ONBOARDING_CHAT_MODEL=google_genai:gemini-3.1-flash-lite
```

The backend sends synthetic chat messages and recent clarifications to the
configured provider through LangChain. The intake instructions live in
`app/skills/onboarding-intake/SKILL.md`. A provider error keeps the current
question open so the message can be retried.

The frontend calls `POST /api/v1/conversations/{conversation_id}/chat` with a
message UUID, the observed conversation revision, the question sequence, and
message content. Resending a recent message with the same UUID is safe.
The chat endpoint persists an accepted decision before saving the answer.
A retry or conversation reload completes an interrupted answer write.

## Model-independent sandbox walkthrough

Restart FastAPI and Vite, open the demo login, and choose the customer persona.
Submit the application form or finish the chat intake and select **Review
application**. The submitted application provides an ID and a document checklist.

Switch to the bank persona and open the application. Continue from Apply,
record your sandbox verification, enter a bank risk assessment, and record the
compliance review. At Risk Review you can request missing information from the
customer, pause, or continue after documenting the decision. The bank prepares
a sandbox agreement and approves its release at Document Review. Switch to the
customer to download and sign it, then return to the bank to provision the
sandbox account. The customer can then open the account summary.

The bank detail page shows audit history, the last workflow revision, and sandbox
action evidence. A failed or interrupted sandbox write can be retried at the same
stage and reconciled against its operation ID. Risk overrides can support a
reviewer-authored guardrail proposal in the Guardrails screen. Approval records
a new policy version. Rule text is stored for review and future agent consumption.

The workflow uses Atlas Managed MCP and needs permission to write the
application, guardrail, and sandbox collections. Each application update stores
its audit entry with the state change. It runs at each customer or bank handoff. Bank-entered risk, compliance review, and sandbox records demonstrate
the handoffs while the model-driven workflow is being built.
